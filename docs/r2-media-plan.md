# R2 media and client upload plan

## Decisions

- Cloudflare R2 is the object source of truth. Tardy stores object keys and verified metadata, never provider URLs as durable identity.
- Clients upload directly to R2 through short-lived S3-compatible presigned requests. Video bytes do not transit the Tardy API.
- Original uploads are private and quarantined. Only validated renditions can be attached to reels or shared.
- Structured Hyperframes scene data plus voiceover is the preferred playback artifact. Pre-rendered video is produced for exports, external sharing, incompatible clients, and explicitly video-native posts.
- Public items are generated once and served many times. Personal agent/notebook media is never promoted into a shared cache namespace.

## Object layout

Object keys are generated by the backend and contain no email, handle, repository name, or user-supplied filename.

```text
private/original/{account_uuid}/{asset_uuid}
private/structured/{account_uuid}/{asset_uuid}/scene.json
private/audio/{account_uuid}/{asset_uuid}/voice.m4a
quarantine/{account_uuid}/{upload_uuid}
public/rendition/{content_digest}/video-720p.mp4
public/rendition/{content_digest}/video-540p.mp4
public/rendition/{content_digest}/poster.webp
```

Public rendition keys are content-addressed so identical outputs generate once. Private keys remain owner-scoped even when content happens to match.

## Upload state machine

```text
authorized -> uploading -> uploaded -> validating -> ready
                                  \-> rejected
authorized/uploading -> expired
ready -> deleted
```

State transitions are deterministic database transactions. R2 notifications may wake validation but are not the source of truth.

### 1. Authorize

`POST /v1/uploads` accepts:

- selected profile and intended media kind;
- MIME type from a strict allowlist;
- exact or maximum byte length;
- optional SHA-256 checksum;
- intended visibility and use (`scene`, `voiceover`, `poster`, `video_original`).

The backend checks account/profile ownership, membership quota, privacy policy, and rate limits. It creates an expiring `upload_sessions` row and returns:

- upload ID and expiry;
- backend-generated object key;
- one presigned PUT for small objects, or multipart part-signing instructions for large video;
- required `Content-Type`, checksum, and length headers;
- maximum allowed size.

Presigned operations allow only the assigned key, method, headers, and short expiry. They never grant bucket listing or arbitrary overwrite access.

### 2. Upload

Clients upload directly to R2. Default thresholds:

- scene JSON: 1 MiB maximum;
- image/poster: 10 MiB maximum;
- voiceover: 25 MiB maximum;
- video original: 250 MiB maximum;
- multipart only above 16 MiB, with bounded part count.

These are backend policy values and must be returned by the authorization response rather than duplicated in clients.

### 3. Finalize

`POST /v1/uploads/{id}/complete` is authenticated and idempotent. Tardy performs an R2 `HEAD`, then verifies key, object existence, length, content type, provider checksum/ETag semantics, and client checksum when supplied. Client-provided metadata alone is never trusted.

Finalization inserts/updates `media_assets`, queues validation through the transactional outbox, and returns `202 Accepted`. It does not make the object feed-visible.

### 4. Validate and render

- Parse structured JSON against a versioned schema with depth/count limits.
- Sniff file signatures instead of trusting MIME extensions.
- Decode media in a resource-bounded worker.
- Reject malformed files, excessive duration/dimensions, active content, and policy violations.
- Strip image metadata and never serve an original user filename.
- Generate posters and bounded 360p/540p/720p H.264 renditions initially. Add HEVC only when client negotiation and encoding economics justify it.
- Record provenance from source asset through each rendition.

## Delivery

- Private objects use short-lived signed GET URLs minted only after the privacy policy authorizes the viewer.
- Public approved renditions use immutable content-addressed URLs behind Cloudflare caching.
- `Cache-Control: public, max-age=31536000, immutable` applies only to public digest-addressed renditions.
- Private responses must not enter shared caches.
- Range requests are enabled for video/audio seeking.
- Scrape/rate controls operate at both API authorization and Cloudflare layers.

Deleting an asset immediately revokes new private URL issuance and records a deletion job. R2 lifecycle rules clean abandoned multipart uploads and expired quarantine objects. Public content-addressed renditions use a reference/retention policy before physical deletion.

## Feed payload and prefetch

Each post advertises available representations:

- versioned structured scene JSON;
- voiceover and duration;
- poster;
- optional video renditions with codec, dimensions, bitrate, and byte length.

The client selects the cheapest compatible representation. It prefetches at most the next one or two items, honors a Wi-Fi-only preference, maintains a byte-bounded LRU cache, cancels downloads when the feed changes, and never prefetches private media after authorization expires.

## Observability

Add bounded-label metrics for:

- upload sessions authorized/completed/expired/rejected by media kind and reason class;
- authorized versus verified bytes;
- R2 request latency and failures by operation;
- validation/render duration and queue depth;
- rendition bytes by codec/resolution;
- signed delivery authorizations and denials;
- outbox and deletion lag.

Never use account, asset, object key, MIME value, or filename as a Prometheus label.

## Implementation order

1. Add PostgreSQL `media_assets`, `upload_sessions`, `media_renditions`, and outbox tables.
2. Define a narrow `ObjectStore`/`UploadSigner` interface and implement it with an established S3-compatible Rust client configured for R2.
3. Ship small-object PUT authorization and idempotent finalization first.
4. Add the isolated validation worker.
5. Add multipart video uploads and stale-upload cleanup.
6. Add structured scene playback and client prefetch before investing in more video renditions.
