# PostgreSQL 17 plan

## Decision

Move all durable Tardy state to PostgreSQL 17 before community mode or billing. SQLite currently persists only onboarding accounts, credentials, claim codes, and account/profile ownership; profiles, reels, live sessions, DMs, blocks, and shares are process memory. PostgreSQL becomes the sole durable source of truth.

Use `sqlx` with checked-in offline query metadata and versioned SQL migrations. Keep the existing `Store` and account-registry interfaces as the application boundary while replacing their implementations. Do not spread SQL into HTTP handlers.

## Initial schema

All identifiers are UUIDs generated by the application. All timestamps use `timestamptz`; external millisecond timestamps are converted at the API boundary.

| Relation | Important constraints |
|---|---|
| `accounts` | unique normalized email; status; created/deleted timestamps |
| `api_credentials` | token digest only; account FK; created, last-used, revoked timestamps |
| `agent_claims` | code digest only; expiry; single-use claim timestamp; optional account FK |
| `profiles` | account FK; case-insensitive unique handle; public fields; lifecycle timestamps |
| `profile_privacy` | one row per profile; profile visibility, DM policy, reshare policy, default content visibility |
| `profile_blocks` | `(blocker_id, blocked_id)` primary key; reject self-blocks |
| `reels` | owner FK; immutable media references; visibility; moderation state; provenance |
| `live_sessions` | owner FK; lifecycle state; playback metadata; next event sequence |
| `live_events` | `(session_id, sequence)` primary key; typed JSON payload; append-only |
| `dm_threads` | stable ID and creation timestamp |
| `dm_participants` | `(thread_id, profile_id)` primary key; exactly two participants enforced by service transaction |
| `direct_messages` | `(thread_id, sequence)` primary key; sender FK; body; append-only |
| `share_grants` | token digest, creator/subject, expiry/revocation; never persist raw bearer token |
| `memberships` | account FK; Free/REAL/SUPER; provider reference; effective interval |
| `super_tardy_slots` | integer primary key constrained to `1..=1000`; unique account assignment |
| `payment_events` | provider + provider event ID unique; immutable receipt for Stripe/x402 idempotency |
| `outbox` | transactional events for AgentMail, ATProto, Stripe follow-up, and x402 work |
| `media_assets` | owner, media kind, privacy, immutable object key, checksum, byte length, validation/moderation state |
| `upload_sessions` | owner, expected type/size/checksum, R2 object key, expiry, multipart state, finalization result |
| `media_renditions` | asset FK; codec/container/resolution/bitrate; immutable object key; byte length |
| `saved_posts` | `(account_id, reel_id)` primary key; original saved timestamp; private and idempotent |
| `external_ai_consents` | account/provider/purpose key; policy version; grant and revocation timestamps |
| `search_documents` | canonical post FK; content digest; searchable public text; indexing lifecycle |
| `search_embeddings` | document/provider/model key; dimensions; vector; source digest and creation time |
| `embedding_jobs` | idempotent outbox-driven indexing attempts, retry state, and visible terminal errors |

Subject references in shares and moderation should use explicit subject type plus subject UUID with service-level validation. Do not create several nullable foreign keys or duplicate a polymorphic subject schema in each feature.

## Privacy and concurrency invariants

- Every query returning profiles, feed items, live events, DMs, or shares goes through the existing privacy policy boundary.
- Blocking wins over visibility and DM preferences.
- Private is the database default for new profile/content settings.
- DM and live-event sequence allocation uses one transaction: lock the parent row, increment `next_sequence`, insert with the returned value. Unique constraints are the final guard.
- Share and API tokens are at least 128 bits of entropy and stored as digests. Expiry and revocation are checked in the query.
- Stripe/x402 webhook IDs are unique so retries are safe.
- SUPER Tardy capacity is enforced by the `super_tardy_slots` table, not a count followed by an insert.
- PostgreSQL row-level security is a defense-in-depth option after application authorization is stable; it does not replace domain tests.

## Indexes

- `profiles (lower(handle))` unique.
- `reels (published_at DESC)` partial indexes by visibility/moderation state.
- `live_sessions (status, started_at DESC)` and owner/time index.
- `live_events (session_id, sequence)` from the primary key.
- `direct_messages (thread_id, sequence)` from the primary key.
- Both directions of block lookup, including `(blocked_id, blocker_id)`.
- Active share lookup by token digest with a partial index for non-revoked grants.
- Outbox `(available_at, id)` partial index for unfinished work.
- Saved posts `(account_id, saved_at DESC)` for private library pagination.
- ParadeDB BM25 index over public, moderation-approved search documents.
- `pgvector` HNSW index over current-model public embeddings; use iterative scans for filtered queries.

Avoid partitioning initially. Add it only from measured retention/query pressure; live events and DMs are candidates later.

## Cutover sequence

1. Add PostgreSQL integration tests against PG17 and implement `PgStore` behind existing traits.
2. Move account registry and all currently in-memory entities into the same PostgreSQL transaction boundary.
3. Add deterministic export/import tooling in Rust plus row-count and content-digest validation.
4. Rehearse against a production-shaped copy and record timings.
5. Enter a short maintenance window, stop writes, checkpoint/copy SQLite, import once, validate, and switch `DATABASE_URL`.
6. Keep the untouched SQLite artifact for rollback. Do not dual-write.
7. Run smoke tests for claim, profile privacy, block, DM, share, reel, and live-event flows before reopening writes.
8. Observe database pool saturation, transaction latency, errors, deadlocks, and outbox lag through `/metrics`.

Because production data is not established yet, the cheapest path is to make this cutover early—before Stripe and community mode increase migration risk.

## Configuration and operations

- `DATABASE_URL` is required in PostgreSQL mode; fail startup if missing.
- Configure a bounded connection pool and statement timeout. Do not infer an unbounded pool from CPU count.
- Run migrations as an explicit release job or startup mode with an advisory lock, never concurrently from every replica without coordination.
- Back up with managed snapshots plus tested logical restore. A backup without a restore drill is not a recovery plan.
- Health remains process-local; readiness must include a bounded `SELECT 1` once PostgreSQL is authoritative.
